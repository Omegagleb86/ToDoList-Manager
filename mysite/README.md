# ToDoList на Django

## Описание проекта

Данный проект представляет собой учебное веб-приложение для управления личными задачами, реализованное на фреймворке Django. Приложение ориентировано на одного пользователя, однако архитектура изначально построена таким образом, чтобы поддерживать полноценную многопользовательскую модель и дальнейшее расширение функциональности.

Основная идея системы состоит в том, что пользователь может:

- создавать тематические списки задач;
- хранить внутри каждого списка отдельные задачи;
- управлять статусами задач;
- сортировать задачи внутри колонок;
- задавать приоритет через признаки важности и срочности;
- просматривать задачи как в виде канбан-колонок, так и в виде матрицы Эйзенхауэра.

Проект разрабатывался как backend-основа приложения ToDoList. При этом для демонстрации работы были добавлены простые HTML-страницы и JSON-эндпоинт.

## Что было сделано

В рамках проекта реализованы следующие части backend-системы:

### 1. Настроен Django-проект

- использован существующий Django-проект `mysite`;
- настроено подключение собственного приложения `tasks`;
- включена собственная модель пользователя;
- настроены локализация и часовой пояс:
  - язык интерфейса: `ru-ru`;
  - часовой пояс: `Asia/Yekaterinburg`.

### 2. Реализована собственная модель пользователя

Создана модель `TodoUser`, унаследованная от `AbstractUser`.

Это решение выбрано потому, что:

- оно архитектурно более гибкое, чем использование стандартной модели `User`;
- позволяет в будущем без проблем добавлять дополнительные пользовательские поля;
- соответствует хорошей практике проектирования Django-приложений.

На текущем этапе в пользовательскую модель добавлено поле:

- `timezone` — часовой пояс пользователя.

### 3. Реализована модель списка задач `TodoList`

Список задач является логической группой задач, например:

- учеба;
- работа;
- домашние дела.

Для модели списка реализованы поля:

- `user` — владелец списка;
- `title` — название списка;
- `description` — описание;
- `color` — цвет списка;
- `icon` — условное название иконки;
- `position` — порядок отображения;
- `is_archived` — признак архивации;
- `created_at` — дата создания;
- `updated_at` — дата обновления.

Также добавлены:

- ограничение уникальности `user + title`;
- индексы для ускорения выборок по пользователю и архивности;
- сортировка списков по позиции и названию.

### 4. Реализована модель задачи `Task`

Задача является центральной сущностью системы и содержит основную бизнес-логику.

Для модели задачи реализованы поля:

- `user` — прямой внешний ключ на пользователя;
- `todo_list` — ссылка на список задач;
- `title` — заголовок задачи;
- `description` — описание;
- `status` — статус задачи;
- `position` — позиция внутри колонки;
- `is_important` — признак важности;
- `is_urgent` — признак срочности;
- `start_date` — дата начала;
- `due_date` — дедлайн;
- `completed_at` — дата завершения;
- `archived_at` — дата архивирования;
- `is_deleted` — признак мягкого удаления;
- `deleted_at` — дата удаления;
- `created_at` — дата создания;
- `updated_at` — дата обновления.

Реализованы фиксированные статусы задачи:

- `queue` — очередь;
- `in_progress` — в работе;
- `done` — выполнено;
- `archived` — архивировано.

Статусы заданы через `choices`, так как набор состояний фиксирован и не должен изменяться пользователем.

### 5. Реализована логика приоритетов по матрице Эйзенхауэра

Приоритет задачи хранится не как одна категория, а как два независимых признака:

- `is_important`;
- `is_urgent`.

Преимущества такого подхода:

- гибкость фильтрации;
- удобство аналитики;
- соответствие логике матрицы Эйзенхауэра;
- отсутствие жесткой привязки к четырем заранее записанным категориям.

На основе этих двух полей задача автоматически интерпретируется как одна из четырех категорий:

- важно и срочно;
- важно, но не срочно;
- срочно, но не важно;
- не срочно и не важно.

### 6. Добавлены ограничения целостности данных

В проекте реализованы базовые механизмы контроля корректности данных:

- задача обязательно принадлежит пользователю;
- задача обязательно принадлежит списку;
- пользователь задачи должен совпадать с владельцем списка;
- позиция задачи должна быть неотрицательной;
- в рамках одного списка и одного статуса позиции задач не должны повторяться;
- дедлайн не может быть раньше даты старта;
- дата завершения не должна быть раньше даты создания.

### 7. Настроена административная панель Django

Для удобства демонстрации и управления данными зарегистрированы в админке:

- пользователи;
- списки задач;
- задачи.

В админке доступны:

- поиск;
- фильтрация;
- сортировка;
- просмотр ключевых полей.

Это позволяет использовать проект не только как программную основу, но и как наглядный backend-прототип.

### 8. Реализованы демонстрационные представления

Для показа работы backend добавлены простые пользовательские страницы:

- главная страница со списком тематических планов;
- страница отдельного списка задач;
- представление задач по статусам в виде канбан-колонок;
- представление задач по матрице важности/срочности;
- JSON-эндпоинт для демонстрации структуры данных.

### 9. Добавлена команда заполнения демо-данными

Реализована management-команда:

```bash
python manage.py seed_demo
```

Она создает:

- тестового пользователя `demo`;
- администратора `admin`;
- несколько тематических списков;
- несколько демонстрационных задач с разными статусами и приоритетами.

## Архитектура системы

### Общая логика

Архитектура системы построена по иерархическому принципу:

**Пользователь -> Список задач -> Задача**

Это означает:

- один пользователь может иметь много списков задач;
- один список задач может содержать много задач;
- каждая задача принадлежит только одному списку;
- каждая задача также напрямую связана с пользователем.

### Почему в задаче хранится ссылка и на список, и на пользователя

Формально пользователя можно определить через `todo_list.user`, однако в проекте дополнительно хранится прямое поле `user` в модели задачи.

Такое решение принято по следующим причинам:

- упрощаются запросы к базе данных;
- ускоряется фильтрация задач по пользователю;
- проще контролировать целостность и доступ;
- такая структура хорошо подходит для будущего API и сериализации.

### Архитектура базы данных

Система включает три основные таблицы:

#### 1. Таблица пользователей

Используется собственная модель `TodoUser`, основанная на `AbstractUser`.

Содержит:

- стандартные поля Django-пользователя;
- дополнительное поле `timezone`.

#### 2. Таблица списков задач

Модель `TodoList` отвечает за тематическое разделение задач.

Основные функции:

- логическая группировка задач;
- хранение пользовательского порядка списков;
- возможность архивирования без удаления.

#### 3. Таблица задач

Модель `Task` хранит:

- содержимое задачи;
- текущее состояние;
- приоритет;
- порядок внутри колонки;
- временные параметры;
- признаки архивирования и мягкого удаления.

Таким образом, эта таблица является центральной частью всей системы.

### Логическая независимость статуса и приоритета

В проекте статус задачи и ее приоритет намеренно разделены.

Это значит:

- статус показывает этап выполнения;
- важность и срочность показывают значимость задачи;
- одна и та же задача может быть:
  - в очереди и одновременно срочной;
  - в работе и одновременно важной;
  - выполненной, но при этом ранее относившейся к высокой приоритетности.

Такой подход делает модель реалистичной и удобной для реального управления задачами.

## Как запустить проект

### 1. Перейти в папку проекта

```bash
cd mysite
```

### 2. Применить миграции

```bash
../.venv/bin/python manage.py migrate
```

### 3. Создать демонстрационные данные

```bash
../.venv/bin/python manage.py seed_demo
```

### 4. Запустить сервер разработки

```bash
../.venv/bin/python manage.py runserver
```

### 5. Открыть проект в браузере

- главная страница: `http://127.0.0.1:8000/`
- админ-панель: `http://127.0.0.1:8000/admin/`
- JSON-демо: `http://127.0.0.1:8000/api/demo/`
